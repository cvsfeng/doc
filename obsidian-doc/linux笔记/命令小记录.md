# nc
nc`netcat`是一个非常强大的网络工具，常被称为“瑞士军刀”。它可以用来建立TCP/UDP连接、端口扫描、数据传输、搭建简易服务器/客户端等。
 ## -lk选项拆解：
- l（--listen）：进入监听模式。nc会绑定到一个指定的端口，等待客户端连接。用法：必须配合端口号，例如==nc -l 1234==表示监听本地1234端口。
- -k（--keep-open或--persistent）：保持监听状态。默认情况下，nc在接受一个客户端连接、连接关闭后就会退出。加上-k 后，及时当前连接断开，nc也会继续监听同一端口，等待下一个客户端连接，从而时间“持久监听”，可以一次处理多个客户端。
完整常用命令形式

```
nc -lk 1234
```
1. 监听本地1234端口
2. 支持IPv4和IPv6（取决于nc版本）
3. 默认是TCP协议。如果要UDP，加-u :==nc -lku 1234==
 - 实际行为
	 - 启动后，nc会等待第一个客户端连接。
	 - 客户端连接上来后：
		 - 客户端输入的内容会显示在服务器终端。
		 - 服务器终端输入的内容会发送给客户端。
		 - 相当于一个简单的双向聊天管道。
	- 客户端断开连接后
		- 没有`-k`：nc立即退出。
		- 有`-k` ：nc继续监听，等待下一个客户端连接，重复上述过程。
## 典型应用场景
### 聊天服务器
服务器：==nc -lk 1234==
客户端：nc 127.0.0.1 1234(多个客户端可以一次连接并聊天)
### 端口扫描
``` 
nc -zv 172.16.117.254 1-10000 #扫描host1-10000的端口（TCP）
nc -zvu 172.16.117.254 1-10000 #扫描host 1-10000的端口（UDP）
```
## 选项
- **-l**（--listen）：监听模式（服务器）。
- **-p**（--source-port）：指定源端口（客户端模式）。
- **-k**（--keep-open）：持久监听（连接断开后继续等待下一个）。**GNU 版支持**，OpenBSD 版不支持（需脚本循环）。
- **-u**：UDP 模式（默认 TCP）。
- **-v**（--verbose）：详细输出（显示连接信息）。
- **-z**：端口扫描模式（不发送数据，只检查端口开闭）。
- **-w 秒**（--wait）：超时设置（连接/读写超时）。
- **-n**：不解析 DNS（只用 IP）。
- **-4** / **-6**：强制 IPv4 或 IPv6。
- **-e program**：执行程序（危险！常用于反弹 shell，如 -e /bin/sh）。
- **-c**：执行命令（ncat 支持）。
- **-q 秒**：连接关闭后等待秒数退出（控制 EOF）。
# curl
curl（全称”client url“）是一个功能强大的命令行工具，用于通过url从服务器传输数据或向服务器传输数据。它支持大量协议，包括HTTP/HTTPS、FTP/FTPS、SCP等等（总共超过20种）。常被称作”数据传输的瑞士军刀“或”HTTP客户端“。具体可详见官网：[点击访问](https://curl.se)
## 基本语法
```
curl [选项] [URL...]
```
- 如果不提供URL，curl从标准输入（stdin）读取数据。
- 支持多个URL（顺序处理，或用--parallel并行）。
- 输出默认到标准输出（stdout），错误到标准错误（stderr）
### 简单示例
```
curl https://example.com
```
这会打印html内容
### 常见选项(按类别分组)

# ps
ps（全称Process Status）是linux/unix系统中最常用的查看进程的命令。它可以显示当前系统中正在运行的进程快照，包括进程ID、用户、cpu/内存占用、命令等。ps是静态查看（一次性快照），不像`top、htop`是动态实时刷新。
ps有多种实现版本（BSD风格、GUN风格、System V风格），不同系统默认选项略有差异，但现在Linux（如Ubuntu、Centos）通常支持混合使用；
## 基本语法
```
ps [选项]
```
- 不加选项默认只显示当前终端（当前Shell会话）下的进程。
- 常用组合：`ps aux`（BSD风格）`ps -ef`（System V风格）
## 选项分类
ps选项分为三种风格（可以混合使用，但某些冲突时以最后为准）
### Unix/System V风格（选项前加-可组合）
- -e 或 -A：显示**所有进程**（包括其它用户的）
- -f：完整格式（full format），显示更多细节（如PPID、命令参数）
- -u：用户导向格式（显示用户名、cpu、内存占用等）
- -l：长格式（long format），显示更多技术细节（如优先级、状态）
- --forest：树状显示进程层次（父子关系）
### BSD风格（选项前不加-）
- a：显示所有用户的进程（包括终端先关的）
- x：显示无终端进程（如守护进程）
- u：用户导向格式（显示更多列，如%CPU，%MEM）
- w：宽屏展示（避免截断长命令）
- f：树状展示（类似--forest）
### GUN风格（长选项，前加--）
- --pid：指定进程ID
- --ppid：指定父进程ID
- --sort：排序（如--sort=-%cpu按CPU降序）
## 最常用组合
- `ps aux`：显示所有进程（BSD风格），用户友好；
- `ps -ef`：显示所有进程（System V风格）格式完整；
### 输出解释
```
USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
```
- USER：进程所属用户
- PID：进程ID（唯一标识，用于kill等）
- %CPU：cpu占用百分比
- %MEM：内存占用百分比
- VSZ（Virtual Memory Size）：虚拟内存大小（KB）
- RSS（Resident Set Size）：驻留内存大小（实际占用物理内存，KB）
- TTY：关联终端（？表示无终端，如守护进程）
- STAT：进程状态（R=运行（Running），S=睡眠（Sleep），T=停止（Stop），Z=僵尸（Zombie），<高优先级（High Priority）、N低优先级（Low Priority）
- START：启动时间
- TIME：累计CPU时间
- COMMAND：启动命令（带参数）
==ps是系统管理/调试的基础命令，配合kill、top、nice使用非常强大==

# top vs htop

## top命令详解
top命令是linux/unix系统内置的实时进程监控工具，提供动态、交互式的进程视图。它显示系统整体资源使用情况（CPU、内存、负载等）和进程列表，按CPU或内存占用排序。top是静态==**`ps`**==的动态升级版，默认3秒刷新一次。
### 基本用法
```
top
```
直接运行进入交互界面。按==`q`==或==Ctrl+C==退出。
### 界面布局（默认）
top界面分为两部分：
#### 汇总区（上半部分）
```
top - 12:34:56 up 1 day, 2:30,  3 users,  load average: 0.10, 0.20, 0.30
Tasks: 200 total,   1 running, 199 sleeping,   0 stopped,   0 zombie
%Cpu(s):  5.0 us,  2.0 sy,  0.0 ni, 92.0 id,  0.5 wa,  0.0 hi,  0.5 si,  0.0 st
MiB Mem :  8000.0 total,  1000.0 free,  5000.0 used,  2000.0 buff/cache
MiB Swap:  2000.0 total,  1900.0 free,   100.0 used
```
- **第一行：** 当前时间、系统运行时间、用户数、负载平均（1、5、15）
- **第二行：** 任务总数（运行、睡眠、停止、僵尸进程）
- **第三行**：cpu使用率（us用户、sy内核、ni低优先级、id空闲、wa IO等待 等）
- **第四/五行**：内存和Swap使用情况
#### 进程列表（下半部分）
列包括：
- PID：进程ID
- USER：用户
- PR：优先级
- NI：nice值
- VIRT：虚拟内存
- RES：驻留内存
- SHR：共享内存
- S：状态（R运行、S睡眠、Z僵尸、T停止）
- %CPU、%MEM：cpu占用、内存占用
- TIME+：累计CPU时间
- COMMAND：命令名称
#### 常用选项（启动时指定）
- -d 秒：设置刷新间隔（例如 top -d 1 每秒刷新）。
- -p PID：只监控指定 PID（可多个，用逗号分隔）。
- -u 用户：只显示指定用户进程。
- -n 次数：运行指定次数后退出（适合脚本）。
- -b：批处理模式（非交互，用于重定向输出，如 top -b -n 1 > top.txt）。
#### 交互命令（在 top 界面中按键）
- h 或 ?：帮助。
- k：杀进程（输入 PID，然后信号，默认 15）。
- r：renice 进程优先级（输入 PID 和 nice 值）。
- M：按内存排序。
- P：按 CPU 排序（默认）。
- T：按累计时间排序。
- c：切换显示完整命令行。
- 1：显示每个 CPU 核心详情。
- f：字段管理（添加/删除/排序列）。
- 空格：立即刷新。
### 示例
```
top -d 1          # 每秒刷新
top -p 1234,5678  # 只监控两个进程
top -b -n 5 > top.log  # 记录 5 次输出到文件
```
## htop 命令详解
**htop** 是 top 的增强替代品，更人性化、美观（彩色、树状视图、鼠标支持）。它不是系统内置，需要手动安装，但功能远超 top。
### 用法
```
htop
```
## 番外：由系统负载引出的一系列信息

### Load Avg（负载平均值）
在`top`命令的第一行（或第二行）显示的load average（简称load avg），格式通常是由三个数字，例如：
```
load average：0.15,0.20,0.25
```

这三个数字分别表示**过去1分钟、5分钟、15分钟**内系统的**平均负载**（average load）
#### 含义
- 负载指的是：出于**可运行状态（runnable）或不可中断睡眠状态（Uninterruptible Sleep，通常是等待IO）** 的进程/ 线程的平均数量；
- 它反映了**CPU和io资源的争用程度**：
	- 如果负载值接近或等于CPU核心数，系统基本满负荷；
	- 如果显著高于核心数，说明有进程在排队等待cpu或io，系统有压力；
	- 单核cpu负载1.0表示刚好满负荷；四核cpu负载4.0才算满负荷；
#### 计算口径
- Linux内核每5秒采样一次当前runnable进程数+uninterruptible sleep进程数；
- 使用==**指数衰减移动平均**==（exponential moving average）计算三个时间窗口的平均值。
	- 1分钟负载衰减较慢，反应短期突发的负载变化。
	- 5分钟和15分钟负载衰减更快，更能反应中长期趋势。
- 注意：负载计数的是线程（而不是进程），多线程程序会贡献多个计数；
- 它不直接等同于cpu使用率：即使cpu使用率100%，如果没有进程排队，负载可能仍低；反之，io密集型任务可能导致高负载但cpu使用率不高；
#### 举例
- ==**load average ：2.0 1.5 1.0**== 在一台4核机器上；
	- 过去1分钟平均有2个线程在争用cpu、io（轻度压力）
	- 过去5分钟和15分钟压力在下降，系统正在恢复；
#### shareLibs(即top中的SHR列)
top进程列表中的SHR列（有时用户会称为sharelibs）表示==**Shared Resident Memory（共享驻留内存）**==
- **含义**：进程当前在物理内存（RAM）中占用的**可被其他进程共享**的那部分内存大小。
- 主要来源是**加载的共享库（shared libraries，如libc.so、libpthread.so等）** 和**共享内存段(shm)**
- 它**不计入进程的独占内存**，多个进程共享同一份共享库时，每进程的SHR会显示相同的值，但实际物理内存只占用一份。
### 共享内存、虚拟内存、驻留内存
top进程列表常见的内存列：

|列名|全称|含义|是否计入进程内存使用统计|
|---|---|---|---|
|**VIRT**|Virtual Memory Size|**虚拟内存**：进程可见的全部地址空间，包括已分配但未使用、已换出到swap、共享库、映射文件等。|不直接反映实际占用|
|**RES**|Resident Set Size|**驻留内存**：进程当前实际占用的**物理内存**（RAM）大小，不包括已换出到swap的部分。|真实物理内存占用|
|**SHR**|Shared Resident Memory|**共享驻留内存**：RES中**可被其他进程共享**的部分（主要是共享库和共享内存）。|实际物理内存只占一份|
#### 详细解释与举例
假设两个进程都加载了相同的共享库libc.so（大小100MB），各自还有独占内存200MB:
1. 虚拟内存（VIRT）：
	1. 进程看到的“理论最大地址空间”
	2. 包含代码、数据、栈、共享库、内存映射文件等；
	3. **特点：** 可以非常大（远超物理内存），因为很多页面只是预留或映射文件；
	4. **举例：** 一个程序加载了大量共享库和映射了大文件，VIRT可能达到几GB，即使实际只用了几十MB。
2. 驻留内存（RES）：
	1. 进程当前真正占据的物理内存页。
	2. RES=独占驻留内存 + 共享驻留内存（SHR）
	3. **举例：** 上面两个进程各自RES ≈ 200MB（独占）+100MB（共享库） = 300MB
		1. 但系统总物理内存占用 ≈ ==200 * 2+100==（共享库只占一份）= 500MB
3. 共享内存（SHR）：
	1. RES中可以被多个进程共同使用的部分；
	2. 主要是共享库和显式创建的共享内存（System V shm或POSIX shm）
	3. **举例：** 上面两个进程的SHR都显示100MB（共享库部分）但实际物理内存只分配100MB
#### 实际查看建议
- %MEM列基于RES计算（RES/总物理内存）
- 如果想知道进程真实独占物理内存：RES - SHR（近似值）
- 高VIRT但低RES：说明进程预留了很多虚拟空间但还没真正使用；
- 高SHR：通常是正常现象（大量使用共享库），不是内存泄漏
这些指标帮助进程判断**内存占用大**（看RES）、**只是预留多**（看VIRT）还是使用大量共享库（SHR）
### 指数衰减移动平均（Exponential Moving Average, EMA）
#### **指数衰减移动平均**
（简称 EMA，或指数加权移动平均 EWMA）是一种**时间序列数据的平滑计算方法**，它用来计算“平均值”，但与普通平均不同的是：**它给予最近的数据更高的权重，而越旧的数据权重越小，并且权重呈指数级衰减**。
这使得 EMA 能**快速响应最新的变化**，同时保留一定的历史信息，非常适合监控像系统负载这种随时间波动但需要平滑显示的指标。
#### 与普通移动平均的对比

- **简单移动平均（Simple Moving Average, SMA）**：取固定窗口内所有数据的等权平均。例如，过去 60 秒的 12 个采样点（每 5 秒一个），直接算算术平均。缺点：对突发的变化反应慢，所有历史数据权重相同。
- **EMA**：没有固定窗口，而是无限延伸的历史，但旧数据的影响会指数级快速衰减（比如每过一段时间，权重减半）。优点：更敏感于近期变化，计算效率高（只需保存上一次的平均值）。
#### EMA 的基本计算公式
标准 EMA 更新公式（每次新数据到来时）：
```
new_EMA = α × 当前值 + (1 - α) × 上一次_EMA
```
- **α**（alpha，平滑因子）：介于 0~1 之间，控制对新数据的敏感度。
    - α 越大 → 对新数据越敏感（反应快，但波动大）。
    - α 越小 → 平滑度越高（反应慢，但更稳定）。
- 等价形式（常用于负载计算）:
```
new_EMA = exp(-Δt / τ) × 上一次_EMA + (1 - exp(-Δt / τ)) × 当前值
```
- Δt：采样间隔（Linux 中是 5 秒）。
- τ（tau，时间常数）：决定“记忆长度”，τ 越大，历史影响越持久。
#### 在 Linux Load Average 中的具体应用
Linux 内核正是用 EMA 计算那三个 load average 值（1分钟、5分钟、15分钟）：
- 每 **5 秒**采样一次当前负载（runnable + uninterruptible 线程数）。
- 使用 **三个不同的时间常数 τ** 来计算三个独立的 EMA：

| 时间窗口  | 时间常数 τ（秒） | 对应 α（近似） | 含义             |
| ----- | --------- | -------- | -------------- |
| 1 分钟  | 60        | ≈0.08    | 短期负载，反应快，对突发敏感 |
| 5 分钟  | 300       | ≈0.017   | 中期负载，较平滑       |
| 15 分钟 | 900       | ≈0.006   | 长期负载，最平滑，反映趋势  |
更新公式（每 5 秒）：
```
load_1min = load_1min × exp(-5/60) + current_load × (1 - exp(-5/60))
```
（5分钟和15分钟类似，只是 τ 不同）这相当于：旧平均值衰减一点，再加上当前值的一小部分。
#### 举例说明

假设系统当前负载（采样值）序列（每5秒一个）： 0, 0, 0, ..., 突然跳到 10（爆发），然后又回到 0。
- **1分钟 EMA（τ=60秒）**：
    - 爆发后迅速升到接近10（因为 α 大）。
    - 爆发结束后，约1分钟内快速衰减回0。
- **5分钟 EMA（τ=300秒）**：
    - 升得慢一些，峰值没那么高。
    - 结束后，需要几分钟才衰减明显。
- **15分钟 EMA（τ=900秒）**：
    - 变化最慢，峰值最低，衰减需要十多分钟。
结果：load average: 8.50, 3.20, 1.10 表示短期高负载，但系统整体在恢复。
这种设计让管理员一眼就能看出：是短暂峰值（1min 高，其他低）还是持续压力（三个都高）。
总之，EMA 是 Linux load average 的核心算法，让它既能及时反映变化，又避免了采样噪声的过度波动。
### Linux Load Average 为什么用“线程数”来衡量？
Linux 的 **load average**（负载平均值）计算公式是：**可运行（Runnable）线程数 + 不可中断睡眠（Uninterruptible Sleep，D-state，通常等待 I/O）线程数** 的指数移动平均。

下面逐一解答你的疑问。
#### 1. 为什么用**线程**（而不是进程）来衡量？

- **Linux 的调度单位是线程**，不是进程。
    - 在 Linux 内核中，调度器（scheduler）管理的对象是 **task_struct**（任务结构体），每个线程（包括主线程）都对应一个独立的 task_struct。
    - 一个进程可以包含**多个线程**（通过 pthread_create 创建），每个线程都可以独立运行、等待资源、被调度。
    - 如果只数进程数量，会严重低估负载：一个单线程进程贡献 1，一个 100 线程的 Java 程序也只贡献 1，显然不公平。
- **历史原因**：
    - Load average 起源于早期的 Unix 系统，那时大多数进程是单线程的，所以“进程数”≈“线程数”。
    - 现代多线程编程普及后，Linux 自然延续用线程计数，更准确反映实际争用情况。
- **举例**：
    - 一个 Nginx/Web 服务器进程可能有 50 个工作线程，同时处理 50 个请求 → 贡献 50 到负载。
    - 如果只数进程，只会算 1，负载显示很低，但实际上系统可能已经很忙。

#### 2. 一个线程是否“占用一个 CPU”？

**不是**。线程是**调度单位**，但不等于“独占一个 CPU 核心”。

- **线程与 CPU 的关系**：
    - 一个线程在某一时刻只能在一个 CPU 核心上运行。
    - 但多个线程可以**并发争用**同一个核心（通过时间片轮转）。
    - 如果线程数 > CPU 核心数，多余的 Runnable 线程就会排队等待 → 这正是负载高的表现。
- **举例**（4 核 CPU）：
    - 同时有 4 个 Runnable 线程 → 负载 ≈4.0，CPU 刚好满负荷，无排队。
    - 有 8 个 Runnable 线程 → 负载 ≈8.0，每个核心平均 2 个线程排队，系统有压力（上下文切换增多，效率下降）。
    - 即使 CPU 使用率 100%，如果没有排队线程，负载可能只有 4.0。

#### 3. 为什么要把“不可中断睡眠（D-state）”线程也算进去？

- D-state 线程通常在等待**磁盘 I/O**（读写硬盘/SSD、网络文件系统等），此时线程不能被信号中断。
- 虽然它们不占用 CPU 时间，但：
    - 它们占用内核资源（进程表槽位、内存等）。
    - 大量 D-state 线程表明 **I/O 瓶颈**，系统整体响应变慢（其他线程可能因等待这些 I/O 而受影响）。
    - 现代系统中，I/O 瓶颈（尤其是慢磁盘）比纯 CPU 瓶颈更常见。
- **举例**：
    - 一个备份程序大量读磁盘 → 几十个线程进入 D-state → 负载升高，即使 CPU 空闲（%CPU 很低）。
    - 这时你会感觉系统“卡顿”，因为新任务也要排队等磁盘。

#### 4. 为什么不用其他指标直接衡量？
| 指标                | 为什么不适合作为 load average 的核心          | 与 load average 的区别                            | 适用场景                     |
| ----------------- | ---------------------------------- | --------------------------------------------- | ------------------------ |
| **CPU 使用率（%CPU）** | 只反映已使用的时间比例，不反映**排队等待**的线程数        | %CPU=100% 时，如果刚好等于核心数，负载=核心数（无压力）；如果线程排队，负载更高 | 查看 CPU 忙闲比例（top 的 %Cpu）  |
| **内存使用量**         | 内存不足的表现是 swap 或 OOM，与 CPU/I/O 争用无关 | 内存高不一定导致线程排队                                  | 用 `free` 或 top 的 Mem 行监控 |
| **磁盘 I/O**        | 太具体，只反映吞吐/延迟，不综合 CPU               | Load average 已间接包含（通过 D-state）                | 用 `iostat`、`iotop` 监控    |
| **网络 I/O**        | 同上，网络等待通常是可中断睡眠（S-state），不计入负载     | 网络瓶颈通常不推高负载（除非底层磁盘网络存储）                       | 用 `netstat`、`iftop`      |
| **进程数量**          | 忽略多线程进程，低估现代应用负载                   | 一个 100 线程进程只算 1                               | 粗略查看系统进程总数（`ps aux       |
**Load average 的设计哲学**：

- 它是一个**简单、历史悠久的综合指标**，旨在回答：“系统当前有多忙？需要排队多久？”
- 它不追求精确的资源使用百分比，而是反映**资源争用程度**（CPU + 关键 I/O）。
- 其他指标更细粒度，但需要多个工具组合查看（top/htop 已提供 %CPU、Mem、I/O 等）。
#### 总结
- 用**线程数**是因为它是 Linux 调度器的真实单位，能准确反映现代多线程应用的负载。
- 加上 D-state 是为了捕捉 I/O 瓶颈这个常见问题。
- Load average 不是万能指标，它和 %CPU、内存等是互补的：**负载高但 %CPU 低 → I/O 瓶颈；负载高且 %CPU 高 → CPU 瓶颈**。
### D-state 是什么？
**D-state** 是 Linux/Unix 系统中进程（或线程）状态的一种，完整名称是 **Uninterruptible Sleep**（不可中断睡眠），在 ps、top、htop 等命令的 **STAT** 列中用大写字母 **D** 表示。

#### D-state 是什么的缩写？

- **正式缩写**：**D** 来自 **Disk sleep**（磁盘睡眠）。
- **更准确的描述**：它是 **TASK_UNINTERRUPTIBLE** 状态的简称（内核源码中定义的常量）。
    - 与之相对的是 **Interruptible Sleep**（可中断睡眠，用 **S** 表示，TASK_INTERRUPTIBLE）。

#### 为什么叫 D-state（为什么用 “D”）？

这是**历史遗留命名**，源于早期的 Unix 系统（上世纪70-80年代）：

1. **历史原因**：
    - 在早期 Unix 中，这种状态最常见的场景是进程正在等待**磁盘 I/O 操作**（如 read/write 系统调用等待硬盘读写完成）。
    - 当时磁盘非常慢（机械硬盘），I/O 操作可能需要几百毫秒甚至秒级时间。
    - 为了避免中断导致**内核数据结构不一致**（例如，正在写的块数据半途被打断，可能损坏文件系统），内核设计为**不可中断**这种等待。
    - 因此，开发者用 **D** 来代表 **Disk**（磁盘），以区分普通的、可被信号中断的睡眠（S-state）。
2. **现代含义**：
    - 虽然现在叫 “Uninterruptible Sleep”，但 **D** 的命名保留了下来。
    - D-state 不仅限于磁盘 I/O，还包括其他**必须不可中断的内核操作**，例如：
        - 某些文件系统操作（NFS、ext4 等）。
        - 部分网络设备驱动等待。
        - 内存页回收（page fault 时某些情况）。
        - 锁原始设备（如直接操作硬件）。
    - **关键特性**：处于 D-state 的进程**不能被普通信号中断**（甚至 kill -9 也无效），必须等到底层内核操作完成才能醒来。
        - 这能保护内核一致性，但也可能导致问题：如果底层驱动卡死，进程会“永久”卡在 D-state（系统卡顿）。
#### 与其他状态对比
| 状态码   | 全称                    | 含义                  | 是否可被信号中断 | 常见原因            |
| ----- | --------------------- | ------------------- | -------- | --------------- |
| **R** | Running/Runnable      | 运行中或可运行（排队等待 CPU）   | 是        | CPU 计算密集        |
| **S** | Interruptible Sleep   | 可中断睡眠（等待事件，如信号、定时器） | 是        | sleep()、等待输入    |
| **D** | Uninterruptible Sleep | 不可中断睡眠（通常等待 I/O）    | 否        | 磁盘/网络 I/O、驱动等待  |
| **T** | Stopped               | 停止（收到 SIGSTOP 或调试）  | 是        | Ctrl+Z、debugger |
| **Z** | Zombie                | 僵尸进程（已结束但未回收）       | -        | 父进程未 wait()     |
#### 实际影响与注意事项

- **高负载贡献**：D-state 线程会计入 load average，因为它们占用系统资源并可能阻塞其他操作。
- **问题诊断**：
    - 大量 D-state 进程 → 通常是 **I/O 瓶颈**（用 iostat、iotop 检查磁盘）。
    - 如果进程长期卡在 D-state → 可能硬件故障、驱动 bug 或 NFS 挂起。
- **举例**：
    - 一个程序执行 dd if=/dev/sda of=file.img（直接读磁盘）时，进程可能进入 D-state。
    - 在 top 中看到 STAT 为 "D" 的进程，表示它正“深度睡眠”，别急着杀（杀不掉），等 I/O 完就好。
这个命名是 Unix 传统的一部分，虽然现在 I/O 不只限于磁盘，但 “D” 已经沿用了几十年。
### 换出到swap
在Linux系统内存管理中（top命令的内存列如RES、VIRT等会涉及这个概念）**换出到swap的部分**指的是：
进程的某些内存页面（pages）因为物理内存（RAM）不足，被操作系统**临时从RAM中移出（swapped out）**，存储到硬盘上的swap空间。这些页面不再占用宝贵的RAM，但进程如果后续需要访问它们，系统会再把它们**换入（swapped in）** 回RAM。
- 关键点：==这部分内存不算在RES（驻留内存）里==，因为RES至统计当前实际驻留在物理RAM中的部分。
- 但它仍计入VIRT（虚拟内存），因为从进程的角度上看，这些内存页面还是属于它的地址空间；
#### swap是什么
Swap（交换空间，swap space）是linux系统在硬盘（HDD/SSD）上预留的一块专用区域（可以是分区或文件），作用类似于windows的页面文件（pagefile.sys）
##### swap主要作用
- 当物理内存（ram）快用完时，内核会选择不活跃的内存页面“换出”到swap，腾出ram给更紧急的进程使用。
- 这能防止系统直接因为内存不足而杀死进程（OOM Killer）让系统在内存压力下继续运行。
##### swap的类型
- Swap分区：独立的硬盘分区（用mkswap创建），性能较好。
- Swap文件：普通文件（用fallocate或dd创建），更灵活
##### 查看系统swap情况的命令：
- free -h ：显示总swap、已用、可用；
- swapon --show ：列出当前启用的swap；
- top或htop的内存也会显示swap总用量.
##### 举例说明
假设一台机器有8GB RAM，运行一个大程序（占用10GB虚拟内存）:
1. 正常情况（ram充足）：
	1. 程序所有活跃页面都在RAM中。
	2. RES ≈ 实际使用量（比如6GB）
	3. swap使用 ≈ 0（没有换出）
2. 内存压力大时（RAM只剩一点）
	1. 内核把程序中不常用的2GB页面换出到swap；
	2. RES降到≈4BG（只剩下RAM中的部分）。
	3. VIRT仍≈10GB（包括换出的2GB）
	4. free -h 会显示swap已用了2GB
如果程序突然需要访问那些2GB换出页面
- 系统先把其他页面换出（腾空间），再把需要的页面换入RAM
- 这会导致明显卡顿（因为硬盘写比RAM慢几百倍），称为swap thrashing（交换风暴）
##### 优缺点与实际建议
- **优点**：防止OOM（内存不足杀进程），适合偶尔内存峰值的场景（如服务器突发负载）
- **缺点**：频繁使用swap会严重拖慢系统性能（IO瓶颈）理想状态是swap使用率接近0；
- **现代建议**：
	- 有足够的ram机器（如16GB+），可以禁用swap或只留少量应急；
	- 云服务器/虚拟机常启用适量swap。
	- 用vm.swappiness参数调整内核换出倾向（默认60，值越小越保守；设置10或0可减少换出）。
总之，“==换出到swap的部分==”就是暂时“赶出ram、存到硬盘的内存“，res不统计它是为了反应进程真实占用物理内存的情况。如果swap使用很高，通常说明需要加ram或优化程序内存了。

### 共享驻留内存（SHR）的机制详解
SHR（Shared Resident Memory）列显示的是进程RES（驻留物理内存）中理论可被其他进程共享的那部分，主要来源有两类：
- **共享库（shared libraries，如libc.so、libpthread.so）**：这些事动态链接库的代码和只读数据段。
- **显式共享内存（如System V shm、mmap的MAP_SHARED映射的文件或匿名共享内存）** 
这两类的共享机制**完全不同**。

1. **如果进程B修改了进程A”共享“来的RES部分，会影响A吗？**
答案：取决于共享类型。大多数情况下（共享库）不会影响A；少数情况下（显示共享内存）会影响。
- 共享库的情况（最常见，占SHR大部分）
	- 共享库的代码段和只读数据段在物理内存中只是**只读（Read-Only）** 的
	- 多个进程（如A和B）映射相同的物理页面，从而节省内存。
	- 如果B试图修改这部分内存（例如误操作写入了共享库的代码区）：
		- 会触发**Copy-on-write（COW，写时复制）** 机制；
		- 内核会立即为B创建一个私有副本（新物理页面），B的修改只发生在自己的副本上。
		- A完全不受影响，仍使用原来的共享页面。
	- 结论：共享库的共享是”安全的“，修改不会相互干扰。这也是为什么几乎所有程序都可以放心加载同一套libc二不担心被其他进程”污染“
- 显示共享内存（较少见，有由程序主动创建）：
	- 这是程序员用 shmget/shmat 或 mmap(..., MAP_SHARED) 主动创建的真正可写共享内存；
	- 多个进程映射相同的物理页面，读写都实时同步；
	- 如果 B 修改了这部分内存，A 会立即看到变化（因为是同一块物理内存）；
	- 这正是共享内存的设计目的（如进程间通信 IPC），但也要求程序员自己同步（用信号量、互斥锁等），否则会出现竞态条件（race condition）；
	- 结论：这里修改是相互可见的，程序必须自己处理一致性。
总结：SHR 列显示的“可共享”只是可能性，实际是否真正共享以及修改是否影响他人，取决于底层映射方式。共享库（默认情况）通过 COW 保护了各自的独立性。
2. 一个进程A的可共享RES部分，最多可以共享给多少个给其他进程？有限制吗？
**答案：理论上没有硬性上限，只要系统资源允许。**
- **共享库**：
    - 一份共享库的物理页面可以被**任意多个进程**同时映射（成千上万个都没问题）。
    - 限制因素只有：
        - 系统总物理内存大小（页面只需一份）。
        - 进程总数限制（Linux 默认 ulimit 可调）。
        - 虚拟地址空间（64 位系统几乎无限制）。
    - 实际例子：一台服务器上运行几千个 Apache/Nginx 进程，都共享同一套 libc、openssl 等库，SHR 很高，但物理内存只占一份。
- **显式共享内存**：
    - 同样没有硬限制，但受以下约束：
        - 共享内存段的总大小受 shmmax、shmall 等内核参数限制（可通过 /proc/sys/kernel/ 调整）。
        - 系统总共享内存上限（通常几 GB 到几十 GB，可配置）。
        - 每个段能 attach 的进程数没有明确限制，但实际受内存和文件描述符限制。
**结论**：没有固定进程数量限制，主要受物理内存、内核参数和系统负载限制。实际生产环境中，共享库可以轻松共享给成千上万个进程。
 3. A 的可共享 RES 部分可以共享给线程吗？
**答案：线程不是“共享给”，而是天然完全共享（因为线程属于同一进程）。**
- 在 Linux 中，**线程（pthread）是轻量级进程**，但它们**共享同一个虚拟地址空间**。
- 这意味着：
    - 进程 A 的所有内存（包括代码、堆、栈外的全局区、共享库、共享内存段）**对 A 的所有线程都是完全可见和共享的**。
    - SHR 中来自共享库的部分，A 的所有线程天然使用同一份。
    - 显式共享内存段也被所有线程共享（常用于多线程程序内部通信）。
- **线程间不需要额外机制**就能访问同一块内存（但仍需同步避免竞态）。
**与进程间共享的区别**：
- 进程间共享需要 mmap 或 shm 机制。
- 线程间是**进程内共享**，开销更小，访问更快。
**总结**：是的，线程会自动、完全共享进程 A 的所有可共享 RES 部分，这是多线程编程的基础优势之一。
### 进程看到的“理论最大地址空间”大小
进程看到的“理论最大地址空间”指的是**进程虚拟地址空间（Virtual Address Space）的上限**，即进程理论上可以寻址的最大内存范围。这个上限**不由物理内存（RAM）大小决定**，而是由 **CPU 架构** 和 **操作系统内核实现** 决定的。

VIRT（top 命令中的虚拟内存列）显示的是进程**当前已映射/使用的虚拟内存总量**，它通常远小于理论上限，但永远不会超过这个上限。
#### 具体大小（Linux 系统主流情况）

| CPU 架构                  | 位数  | 用户态虚拟地址空间理论上限                          | 备注                                                                        |
| ----------------------- | --- | -------------------------------------- | ------------------------------------------------------------------------- |
| x86 (32 位)              | 32  | 4 GiB（2³² 字节） 用户态通常只有 ≈3 GiB           | 内核态占 1 GiB（高地址）。现代系统已很少使用 32 位进程。                                         |
| x86_64 (64 位)           | 64  | **128 TiB**（2⁴⁷ 字节 ≈ 131,072 GiB）      | 当前主流（默认 4-level page table）。 地址范围：0x0000000000000000 ~ 0x00007fffffffffff |
| x86_64 (5-level paging) | 64  | **64 PiB**（2⁵⁶ 字节 ≈ 72,057,594 GiB）或更高 | 需要内核支持（Linux 5.4+ 可启用，较新发行版如 Ubuntu 22.04+、RHEL 9+ 支持）。地址范围扩展到 2⁵⁷ 或更多。   |
#### 关键解释

1. **为什么 64 位不是 2⁶⁴（≈18.4 EB）？**
    - 虽然是 64 位地址，但当前硬件和 Linux 内核只实现了**部分位数**（称为 canonical address）。
    - 默认使用 **48 位虚拟地址**（用户态 47 位有效），所以是 128 TiB。
    - 未来可能扩展到完整 64 位，但目前硬件（Intel/AMD CPU）最多支持 57 位左右。
2. **用户态 vs 内核态**
    - 虚拟地址空间被分成两半：
        - **用户态**（低地址）：进程自己的代码、数据、堆、栈、共享库等。上面表格中的上限指用户态。
        - **内核态**（高地址）：内核代码和数据，进程不能直接访问。
    - 在 64 位系统上，用户态和内核态各占一半（或类似比例）。
3. **实际限制因素（为什么进程达不到理论上限）**
    - **保留区域**：地址空间中有很多保留区（如零页、vsync、guard pages）。
    - **内核参数**：如 ulimit -v 可以人为限制单个进程的虚拟内存。
    - **系统资源**：即使理论允许，分配过多虚拟内存也会耗尽页表（page table）内存，导致性能问题或 OOM。
    - **实际观测**：大多数进程的 VIRT 只有几 GB 到几十 GB，即使是大型程序（如 Chrome）也很少超过几百 GB。
#### 举例
- 一个普通 64 位进程（如 bash）：
    - VIRT 通常几百 MB ~ 几 GB。
    - 但它**理论上可以可寻址**高达 128 TiB（如果系统允许分配那么多）。
- 一个极端例子：某些科学计算程序或数据库可能映射大文件，VIRT 达到几十 TB，但仍远低于 128 TiB 上限。
#### 如何查看自己系统的情况
- cat /proc/cpuinfo 查看架构（flags 中有 lm 表示 64 位）。
- ulimit -v 查看当前 shell 的虚拟内存限制（unlimited 表示无限制）。
- `用 pmap <pid> 或 cat /proc/<pid>/maps 查看具体进程的地址映射。`
总之，在现代 64 位 Linux 系统上，**进程理论最大地址空间是 128 TiB（用户态）**，远超任何实际需求，这也是为什么 VIRT 可以“很大”却不一定消耗物理内存的原因。如果你的系统启用了 5-level paging，上限会更高。

### 进程间共享内存的两种主要机制详解
在 Linux/Unix 系统中，**进程间共享内存（Inter-Process Shared Memory）** 是进程间通信 (IPC) 最快的方式之一，因为它允许多个进程直接访问同一块物理内存，而不需要内核复制数据（不像管道或消息队列）。

你提到的 **shm 机制** 和 **mmap 机制** 是两种经典的实现方式：
1. **System V 共享内存（shm）**：传统的 System V IPC 机制。
2. **mmap 机制**（特别是带 MAP_SHARED 标志的内存映射）：更现代、灵活的 POSIX 方式，常结合文件或匿名映射使用。
还有一种 **POSIX 共享内存**（shm_open + mmap），它是 mmap 的变体，更符合 POSIX 标准。下面逐一详解。
#### 1. System V 共享内存（shm 机制）

这是最早的共享内存实现，来自 System V Unix（上世纪80年代），Linux 完全支持。
**核心函数**（在 <sys/shm.h> 中）：
- shmget()：创建或获取一个共享内存段。
- shmat()：将共享内存段附加（attach）到进程的虚拟地址空间。
- shmdt()：脱离（detach）共享内存段。
- shmctl()：控制（如删除）共享内存段。

**工作流程**：
1. **创建/获取段**：
    - 一个进程（通常是“主”进程）调用 shmget(key, size, flags) 创建一个共享内存段。
        - key：一个整数标识符（常用 IPC_PRIVATE 或 ftok() 生成唯一 key）。
        - size：段的大小（字节）。
        - flags：如 IPC_CREAT | 0666（创建并设置权限）。
    - 返回一个共享内存 ID（shmid）。
2. **附加到进程**：
    - 调用 shmat(shmid, NULL, 0) 返回一个指针（void*），进程可以通过这个指针直接读写内存。
    - 多个进程用同一个 key/shmid 附加同一段，实现共享。
3. **使用**：
    - 所有附加的进程看到同一块物理内存，修改实时可见。
4. **清理**：
    - 用 shmctl(shmid, IPC_RMID, NULL) 标记删除（当最后一个进程 detach 后才真正释放）。
**特点**：
- **优点**：简单、历史悠久，支持权限控制。
- **缺点**：需要手动管理 key，清理麻烦（容易遗留“孤儿”段，用 ipcs -m 和 ipcrm 查看/删除）。
- **同步**：程序员必须自己用信号量（semaphore）或锁防止竞态。
**举例代码**（C语言，两个进程共享一个整数）：
```
// 进程 A（创建并写入）
#include <sys/shm.h>
int shmid = shmget(IPC_PRIVATE, sizeof(int), IPC_CREAT | 0666);
int *shared = (int*)shmat(shmid, NULL, 0);
*shared = 42;  // 写入
// ... 通知进程 B ...
shmdt(shared);

// 进程 B（读取）
int shmid = shmget(同一key, 0, 0);  // 获取已有段
int *shared = (int*)shmat(shmid, NULL, 0);
printf("%d\n", *shared);  // 输出 42
shmdt(shared);
```
#### 2. mmap 机制（内存映射共享）

mmap() 是更现代的机制（来自 BSD Unix），它将文件或匿名内存映射到进程地址空间。结合 MAP_SHARED 标志即可实现进程间共享。
**核心函数**（在 <sys/mman.h> 中）：
- mmap(addr, length, prot, flags, fd, offset)：映射内存。
    - flags：关键是 MAP_SHARED（共享修改实时可见）或 MAP_PRIVATE（私有，写时复制）。
- munmap()：解除映射。
**两种共享方式**： a. **基于文件的共享映射**（最常见）：
- 先创建一个文件（或用 /dev/shm 中的 tmpfs 文件）。
- 多个进程用同一个文件和 offset 映射，带 MAP_SHARED。
b. **匿名共享映射**（不依赖文件）：
- 用 MAP_ANONYMOUS | MAP_SHARED 直接创建匿名段（无需文件描述符 fd=-1）。
**工作流程**（匿名共享为例）：
1. **父进程创建**：
    - void *ptr = mmap(NULL, size, PROT_READ|PROT_WRITE, MAP_SHARED|MAP_ANONYMOUS, -1, 0);
    - 返回指针，父进程可读写。
2. **子进程继承**：
    - fork() 后，子进程自动继承映射（同一物理页面）。
3. **非亲缘进程**：
    - 用基于文件的映射：先 open() 一个文件，多个进程 open 同一文件后 mmap。
**特点**：
- **优点**：
    - 灵活（可映射文件，实现持久化）。
    - 性能高（零拷贝）。
    - 支持大段内存。
    - 匿名映射无需 key 管理。
- **缺点**：需要同步机制（可用 POSIX 信号量或 futex）。
- **POSIX 变体**（推荐现代程序）：
    - 用 shm_open() 创建“/dev/shm" 中的文件（如 O_RDWR | O_CREAT）。
    - ftruncate() 设置大小。
    - 然后 mmap(..., MAP_SHARED, fd, 0)。
    - 用 shm_unlink() 删除。
**举例代码**（匿名共享，父子进程）：
```
// 父进程
void *shared = mmap(NULL, 4096, PROT_READ|PROT_WRITE, MAP_SHARED|MAP_ANONYMOUS, -1, 0);
int *data = (int*)shared;
*data = 100;

pid_t pid = fork();
if (pid == 0) {  // 子进程
    printf("%d\n", *data);  // 输出 100
    *data = 200;    // 修改，父进程可见
} else {  // 父进程
    sleep(1);
    printf("%d\n", *data);  // 输出 200
}
munmap(shared, 4096);
```
#### 两种机制对比

| 方面   | System V shm     | mmap (MAP_SHARED)     |
| ---- | ---------------- | --------------------- |
| 标准   | System V（较老）     | POSIX/BSD（更现代）        |
| 创建方式 | shmget + key     | mmap + 文件或匿名          |
| 清理   | shmctl(IPC_RMID) | munmap + unlink（文件方式） |
| 持久化  | 非持久（重启丢失）        | 文件方式可持久               |
| 灵活性  | 一般               | 高（支持大文件、部分映射）         |
| 推荐场景 | 老系统、简单共享         | 现代程序、需要持久化或大内存        |

**注意事项**：
- 共享内存**无内置同步**，必须配合信号量（sem）、互斥锁（mutex）或原子操作。
- `调试工具：ipcs -m 查看 System V 段；/proc/<pid>/maps 查看进程映射。`
- 性能：共享内存是最快的 IPC（接近进程内访问速度）。
这两种机制是 Linux 共享内存的核心
### 用户态 vs 内核态：虚拟地址空间的划分详解
在 Linux（以及大多数现代操作系统）中，每个进程都有一个独立的**虚拟地址空间**（Virtual Address Space），大小由 CPU 架构决定。这个空间被严格分成两部分：**用户态（User Space）** 和 **内核态（Kernel Space）**。

- **用户态**：进程自己的代码、数据、堆、栈、共享库等所在区域。用户程序（进程）可以直接访问这里，但**不能直接访问内核态**（尝试会触发段错误或权限异常）。
- **内核态**：操作系统内核代码、数据结构、驱动等所在区域。只有在**特权模式**（如系统调用、中断、异常）下才能访问。内核态地址对用户进程是“不可见”和“不可写”的。

这种划分是**硬件+操作系统**共同实现的，主要目的是**隔离保护**：防止用户程序恶意或意外破坏内核，确保系统稳定。

#### 划分原则：为什么“分成两半”？

- 虚拟地址空间被分成**低地址（用户态）** 和 **高地址（内核态）** 两部分，中间往往有“空洞”（非规范地址，用于错误检测）。
- 切换：用户态代码运行在 Ring 3（低特权级），内核态运行在 Ring 0（高特权级）。系统调用（如 syscall 指令）会触发 CPU 模式切换。
- **好处**：
    - 安全：用户程序无法直接读写内核内存。
    - 高效：内核映射对所有进程共享（每个进程的内核态地址相同，但映射同一物理页面）。
    - 上下文切换快：系统调用时只需切换栈和权限，不用换页表。

#### 具体划分方式（以主流架构为例）
| 架构                       | 虚拟地址位数     | 用户态地址范围（低地址）                            | 内核态地址范围（高地址）                            | 用户态大小   | 内核态大小   | 备注                      |
| ------------------------ | ---------- | --------------------------------------- | --------------------------------------- | ------- | ------- | ----------------------- |
| **x86 (32位)**            | 32位        | 0x00000000 ~ 0xbfffffff                 | 0xc0000000 ~ 0xffffffff                 | ≈3 GiB  | 1 GiB   | 经典 3:1 划分（可配置为 4:0，但罕见） |
| **x86_64 (64位，默认48位地址)** | 64位（有效48位） | 0x0000000000000000 ~ 0x00007fffffffffff | 0xffff800000000000 ~ 0xffffffffffffffff | 128 TiB | 128 TiB | 当前主流，几乎“对半分”，中间有巨大空洞    |
| **x86_64 (5级页表扩展)**      | 64位（有效57位） | 扩展到更高（如 0x0000... ~ 更大范围）               | 相应高地址扩展                                 | 可达数 PiB | 相应扩展    | 新内核/硬件支持（如 Linux 5.4+）  |
##### 详解 x86_64（64位，最常见）

- **总虚拟地址**：理论 2⁶⁴，但当前硬件只用 48 位（称为“规范地址” canonical）。
    - 最高位（第47位）决定区域：
        - 如果地址的 bit 47 = 0 → 用户态（低半部分）。
        - 如果 bit 47 = 1 → 内核态（高半部分）。
    - 中间非规范地址（bit 47 不一致）会触发异常（General Protection Fault）。
- **用户态**（低 128 TiB）：
    - 包含：代码段、数据段、堆（malloc）、栈、共享库（libc 等）、mmap 映射文件。
    - 进程的大部分内存都在这里。
- **内核态**（高 128 TiB）：
    - 包含：内核代码、物理内存映射（direct mapping）、vmalloc 区、模块、内核栈等。
    - 所有进程的内核态映射**完全相同**（共享内核物理页面）。
- **空洞**：从 0x0000800000000000 到 0xffff7fffffffffff 是无效的（约 128 TiB × 2 的空洞），用于捕获指针错误。

##### 32位系统的经典划分（历史参考）

- 用户态：0 ~ 3GB（进程可见最大 ≈3GB）。
- 内核态：3GB ~ 4GB（固定 1GB，包含内核镜像、物理内存映射等）。
- 为什么 3:1？早期内核较小，留更多给用户；现代 32 位已淘汰。
#### 举例说明

1. **查看进程地址空间**（用命令）：
    - `运行 cat /proc/<pid>/maps（替换 <pid> 为你的进程 ID，如 bash 的 PID）。`
    - 示例输出（简化）：
```
555555554000-555555556000 r-xp ...  /bin/bash   ← 用户态：代码段（可执行）
555555756000-555555757000 rwxp ...              ← 用户态：数据/堆
7ffff7a00000-7ffff7bcd000 r-xp ...  libc.so     ← 用户态：共享库（低地址）
7ffff7ffd000-7ffff7fff000 rwxp ...              ← 用户态：栈
ffffffffff600000-ffffffffff601000 r-xp ...       ← 内核态：vdso（虚拟动态共享对象）
ffff800000000000-ffffffffffffffff ---p ...       ← 内核态：内核区域（高地址）
```
- 你会看到用户地址在低端（以 0000 或 7fff 开头），内核地址在高端（ffff 开头）。 
1. **进程访问示例**：
    - 用户程序试图访问内核地址（如指针 0xffff800000000000）：
        - 直接崩溃（Segmentation Fault），因为 CPU 在用户模式下禁止访问高地址。
    - 系统调用（如 read()）：
        - 用户代码执行 syscall 指令 → CPU 切换到内核模式 → 进入内核态地址（如内核函数）执行 → 返回用户态。
        - 整个过程用户代码“看不见”内核地址细节。
2. **实际场景**：
    - 一个普通进程（如 Chrome）：
        - VIRT ≈ 几 GB ~ 几十 GB，全在用户态。
        - 试图 malloc 超大内存：可能触及用户态上限（128 TiB，实际远达不到）。
    - 内核模块加载：只出现在内核态高地址，所有进程共享。

这种划分是现代操作系统的核心安全机制（KASLR 等还会随机化内核基址进一步防护）。如果你的系统是 ARM 或其他架构，划分类似但地址范围不同（如 AArch64 用户态 39/42/48 位可选）。

### 如果进程A创建了共享内存段后，进程A突然被kill了，那么这个共享内存段会被如何处理？
如果进程 A 创建了一个 System V 共享内存段（通过 shmget()），然后进程 A 被突然杀死（kill、kill -9 或崩溃退出），**共享内存段不会自动被销毁**。它会继续存在于内核中，直到被显式删除或系统重启。

#### 详细处理机制

System V 共享内存（以及其他 System V IPC 对象，如消息队列、信号量）的生命周期是**内核持久的**（kernel-persistent），设计原则是：

- 一旦创建成功，共享内存段就成为系统级资源，**不依赖于任何进程的存活**。
- 进程退出（正常或被 kill）时，内核会自动：
    - **detach** 该进程 attach 的共享内存段（即 shmdt() 效果）。
    - 但**不会删除段本身**。
- 段的销毁条件（两者必须同时满足）：
    1. 被显式标记为删除：通过 shmctl(shmid, IPC_RMID, NULL)。
    2. 所有 attach 该段的进程都已经 detach（引用计数降为 0）。
- 如果**没有调用 IPC_RMID** 标记删除，即使所有进程都退出或被 kill，共享内存段仍然会保留在系统中（成为“孤儿”IPC 对象），继续占用内核内存。

#### 后果与实际影响

- **资源泄漏风险**：
    - 段会一直占用系统内存（size 指定的大小）。
    - 如果反复创建而不删除，会耗尽 System V IPC 资源（受内核参数 shmmax、shmall 等限制）。
- **其他进程还能使用吗？**
    - 如果其他进程知道 **shmid 标识符**（key）或 **shmid**，仍然可以 shmget() 获取并 attach 使用。
    - 如果使用 IPC_PRIVATE 创建（私有 key），非子进程通常无法获取（子进程在 fork 前可能继承描述符，但 kill 后可能丢失）。
    - 如果使用 ftok() 生成的 key，且 key 基于文件路径等，理论上其他进程可以重新生成相同 key 来获取。
- **查看和手动清理**：
	1、用命令查看现有共享内存段：
```
        ipcs -m          # 查看所有共享内存段（显示 shmid、key、size、拥有者等）
```

	2、手动删除
```
ipcrm -m shmid   # 用 shmid 删除
ipcrm -M key     # 用 key 删除（key 为十六进制）
```
 
#### 举例说明

假设进程 A 执行以下代码创建段：
```
#include <sys/shm.h>
int main() {
    int shmid = shmget(IPC_PRIVATE, 4096, IPC_CREAT | 0666);  // 创建 4KB 私有段
    // 或用 key = ftok("/tmp", 123); shmget(key, ...)
    // 未调用 shmctl(shmid, IPC_RMID, NULL) 标记删除
    sleep(100);  // 模拟运行
    return 0;
}
```
1. 进程 A 运行时，段存在（ipcs -m 可看到）。
2. `你用 kill -9 <pid> 杀死进程 A：`
    - 进程 A 立即终止，内核自动 detach（如果它 attach 过）。
    - **共享内存段仍然存在**，ipcs -m 还能看到它。
    - 系统内存中仍占用 4KB（加上内核开销）。
3. 如果不手动 ipcrm，重启系统前它一直都在。
4. 正确做法（避免泄漏）：
    - 在进程正常退出前调用 shmctl(shmid, IPC_RMID, NULL); 标记删除。
    - 或在信号处理函数（捕获 SIGTERM 等）中删除。
    - 标记后，如果还有其他进程 attach，段会在最后一个 detach 时才真正销毁。
#### 建议（生产环境）
- **总是显式删除**：创建者负责在适当时候调用 IPC_RMID（即使是临时段）。
- **使用 POSIX 共享内存**（shm_open() + mmap()）更现代，它支持自动清理（shm_unlink() 后立即删除，无论 attach 情况）。
- **监控工具**：定期检查 ipcs -m，或用脚本清理孤儿段。

这就是 System V shm 的经典“持久性”设计（历史原因），也是为什么很多人觉得它“麻烦”。如果你的场景是现代程序，推荐切换到 POSIX 共享内存或 mmap 匿名共享。

### 为什么每个进程都有“对应的”内核态区域？

你的疑问很经典，这是操作系统虚拟内存管理的核心设计之一。简单来说：**每个进程的虚拟地址空间确实都包含内核态区域，但这些内核态区域在所有进程中是“相同的映射”**——它们指向**同一套物理内存页面**（内核代码、数据结构、驱动等只存在一份）。

这不是“每个进程复制一份内核代码”，而是**所有进程共享同一份内核物理内存**，通过页表（page table）机制实现“看起来像自己的”。

#### 核心原因：隔离 + 共享 + 高效切换

1. **进程隔离（Isolation）**：
    - 每个进程必须有**独立的虚拟地址空间**，防止进程 A 访问/修改进程 B 的内存（安全性和稳定性）。
    - 如果没有独立的地址空间，所有进程直接用同一套物理地址，进程间就无法隔离（一个进程崩溃可能拖垮整个系统）。
    - 内核态作为地址空间的一部分，也需要“看起来”属于进程，但实际共享。
2. **内核资源共享（Sharing）**：
    - 内核代码、数据结构、驱动是**全局的、固定的**（整个系统只有一份）。
    - 通过页表，所有进程的内核态虚拟地址（如高地址 0xffff...）都映射到**相同的物理页面**。
    - 结果：物理内存只占用一份内核代码，但每个进程“以为”它是自己的地址空间的一部分。
3. **高效上下文切换（Efficiency）**：
    - 系统调用、中断、异常时，需要从用户态切换到内核态。
    - 如果内核态是共享映射的：
        - 只需切换 CPU 模式（Ring 3 → Ring 0）和栈（用户栈 → 内核栈）。
        - **不需要完全切换页表**（或只切换 CR3 寄存器的低位部分，在现代优化如 PCID 中几乎无开销）。
    - 如果不这样设计（比如内核地址完全独立或不映射），切换时需要额外加载页表，性能差得多。

#### 你提出的“直接读取对应的地址再加载”为什么不行？

- **“直接读取固定地址”**：
    - 用户进程在用户模式下，CPU 硬件禁止访问内核虚拟地址（尝试会触发页面故障或保护异常）。
    - 如果让用户进程“直接读取内核物理地址”，会破坏隔离（用户程序能随意读写内核，系统瞬间不安全）。
- **“加载”问题**：
    - 内核不是每次系统调用都“重新加载”代码（那太慢）。
    - 内核代码常驻内存，所有进程共享映射，即时可用。
    - 你的想法类似“所有进程用同一地址空间”，但那会完全丧失进程隔离（早期单任务系统如 DOS 就是这样，但现代多任务 OS 必须隔离）。

#### 页表机制详解（如何实现共享）

- 每个进程有自己的**页表**（page table，存储在内核内存中）。
- 页表条目：
    - 用户态地址 → 映射到进程独占的物理页面。
    - 内核态地址 → 映射到**全局内核物理页面**（所有进程页表中这一部分几乎相同）。
- 当进程切换时：
    - 内核加载新进程的页表（CR3 寄存器指向新页表）。
    - 用户态变了（隔离），内核态不变（共享）。

#### 举例说明

假设一台 64 位 Linux 系统，内核代码物理地址在 0x10000000 ~ 0x11000000。

- 进程 A 的虚拟地址：
    - 用户态：0x0000... ~ 0x00007fff... → 映射到 A 的私有物理页面。
    - 内核态：0xffff8000... ~ 0xffffffff... → 映射到内核物理页面（包括 0x10000000 的代码）。
- 进程 B 同理：
    - 内核态虚拟地址相同，也映射到同一个 0x10000000。
- 系统调用（如 write()）：
    - 进程 A 执行 syscall → CPU 进入内核模式 → 执行内核代码（物理 0x10000000）。
    - 进程 B 同理，用同一份代码。
    - 物理内存只一份内核代码，节省大量 RAM。

| 方面       | 如果每个进程复制内核代码 | 实际设计（共享映射）     |
| -------- | ------------ | -------------- |
| **内存占用** | 巨大（每个进程复制一份） | 最小（全局一份）       |
| **隔离性**  | 好（但没必要）      | 好（用户态隔离，内核态保护） |
| **切换开销** | 高（需加载不同内核）   | 低（共享映射）        |
| **安全性**  | 高            | 高（硬件保护用户不能访问）  |
总之，这种设计是“鱼与熊掌兼得”：进程隔离（用户态独立） + 资源共享（内核态全局） + 高效（快速切换）。这是现代 OS（如 Linux、Windows）的标准实践。如果你想看具体进程的映射，可以用 cat /proc//maps 命令观察内核部分（如` [kernel kcore] 或 vdso`）
###  为什么新任务要排队等磁盘，导致系统“卡顿”？
当系统中有大量线程进入 **D-state**（Uninterruptible Sleep，通常是等待磁盘 I/O）时，你会感觉到整体“卡顿”，不仅仅是因为那些旧线程在等盘，新任务（新进程/线程）也往往被迫“排队等磁盘”。这不是字面上的“所有新任务都直接等磁盘”，而是多重机制叠加导致的连锁反应。下面详细解释原因。

#### 1. **磁盘 I/O 是共享的串行瓶颈资源**

- 磁盘（尤其是机械硬盘 HDD，SSD 也好不到哪里去）**并发能力有限**：
    - HDD：磁头移动是机械操作，一次只能服务有限请求（队列深度通常 32~128）。
    - SSD：虽然快，但内部控制器也有并发限制（队列深度数百到数千，但仍有限）。
- 内核维护一个 **I/O 请求队列**（elevator algorithm 或现代的 mq-deadline/CFQ 等调度器）。
- 当大量线程发出磁盘读写请求（read/write 系统调用）：
    - 旧请求已排满队列 → 新请求只能**加入队列尾部等待**。
    - 新任务如果涉及任何磁盘操作（读文件、加载库、写日志、页面换入等），其线程会直接进入 D-state，**阻塞等待**。
- **结果**：新任务启动后立即“卡住”，感觉系统无响应。

#### 2. **D-state 线程占用关键资源，导致间接阻塞**

- D-state 线程虽然不占用 CPU，但它们**持有内核资源**：
    - 文件描述符、缓冲区、锁（mutex、spinlock）。
    - 内存页（如果在等待页面从磁盘换入）。
- 新任务可能**依赖这些资源**：
    - 例如：一个数据库进程有 50 个线程在等磁盘读数据，它们持有数据库锁 → 新查询线程想访问同一数据，必须等锁释放 → 间接排队。
    - 另一个例子：大量 D-state 线程导致内核 I/O 子系统拥堵，调度器优先处理现有队列，新请求延迟更高。
- 在多线程/多进程应用中常见：一个大文件拷贝占用磁盘，其他程序的普通文件访问（如打开配置文件）也会慢。

#### 3. **系统整体响应变慢的连锁效应**

- **调度器影响**：D-state 线程不参与 CPU 调度，但它们推高 load average（因为计入负载），让调度器认为系统“忙”，可能调整优先级。
- **页面故障（Page Fault）放大**：如果内存压力大，磁盘还负责 swap（交换），D-state 会进一步拖慢页面换入，新任务 malloc 或访问内存时更容易触发 page fault → 等磁盘。
- **用户感知**：鼠标移动、键盘输入等看似不涉及磁盘的操作，也会卡顿，因为：
    - GUI 程序需要读图标/字体/配置（磁盘）。
    - 内核处理中断时，如果底层驱动在等磁盘，会延迟。

#### 举例说明

1. **典型场景：拷贝大文件（dd 或 cp）**
    - 一个进程用 dd if=/dev/sda of=backup.img 狂读磁盘 → 线程进入 D-state，占满 I/O 队列。
    - 你同时打开浏览器：
        - 浏览器加载页面 → 需要读缓存文件、插件 → 新 I/O 请求排队等磁盘 → 浏览器启动慢、页面卡顿。
        - 感觉整个桌面“冻结”几秒。
2. **数据库/服务器场景**
    - MySQL 有 100 个查询线程在等慢磁盘读数据（D-state）。
    - 新连接进来 → 需要读元数据或日志 → 排队等磁盘 → 响应延迟从 ms 变 s。
3. **极端：I/O 风暴（thrashing）**
    - 多个进程同时大量 I/O → 队列满 → 新任务几乎所有磁盘操作都阻塞 → 系统近乎“死机”（直到队列消化）。

#### 如何缓解/诊断

- **诊断**：
    - iostat -x 1：看磁盘利用率（%util ≈100% 表示瓶颈）和 await（等待时间）。
    - iotop：看哪些进程在狂用 I/O。
    - vmstat 1：看 bi/bo（块输入输出）和 wa（等待 I/O 的 CPU 时间）。
- **缓解**：
    - 用更快磁盘（SSD > HDD）。
    - 限速 I/O（ionice 设置优先级）。
    - 优化程序（异步 I/O、缓存）。
    - 加 RAM 减少 swap。

总之，新任务“排队等磁盘”是因为磁盘是**共享瓶颈** + **资源依赖**，大量 D-state 线程会让整个 I/O 子系统拥堵，波及所有后续操作。这就是为什么 I/O 瓶颈比 CPU 瓶颈更让人觉得“卡顿”（CPU 高时至少还能响应中断，I/O 高时连中断都可能延迟）。
### top 命令中 sy 值详解
在 top 命令的 CPU 使用率总结行（%Cpu(s):）中，**sy** 表示 **system**（内核态/系统时间）占比，单位是百分比（%）。

#### sy = 3.5% 是否表示“系统调用 CPU 占比为 3.5%”？

- **不完全准确**，但很接近。
    - sy 统计的是 CPU 在**内核态（kernel mode）**执行的时间占比，包括：
        - 用户进程的**系统调用**（syscall，如 read/write/open/mmap 等）。
        - **内核线程**（kworker、ksoftirqd 等）的执行。
        - **中断处理**（hardirq 和 softirq，包括驱动、网络、定时器等）。
        - 其他内核操作（如调度、内存管理）。
    - 其中，**系统调用**是 sy 的主要来源之一，但不是全部。
    - 所以 sy=3.5% 表示：**CPU 时间中有 3.5% 用于内核态代码执行**（广义的“系统开销”），而非严格只算“系统调用”。

#### 这个数值高还是低？

- **3.5% 是非常低的**，属于**正常甚至优秀的范围**。
    - **典型参考值**（多核系统，日常负载）：
        
        |sy 值范围|评价|常见场景|
        |---|---|---|
        |0% ~ 5%|低（理想）|纯计算任务、轻负载服务器、桌面闲置|
        |5% ~ 15%|中等（正常）|普通 Web/数据库服务器|
        |15% ~ 30%|高（需关注）|高 I/O、网络密集、虚拟化环境|
        |>30%|很高（问题）|系统调用风暴、驱动 bug、I/O 瓶颈|
        
    - 3.5% 表示内核开销很小，CPU 大部分时间用于：
        - 用户程序（us 高）：计算任务。
        - 空闲（id 高）：系统不忙。
        - 或等待 I/O（wa 高，但 wa 不计入 sy）。
    - **结论**：3.5% 完全正常，不用担心。低 sy 说明系统高效，内核干预少。

#### 如何查看 sy 为什么占用 3.5%（原因分析）？

sy=3.5% 虽低，但如果你想深挖具体原因（哪些内核操作贡献了这个 3.5%），可以用以下工具和方法（从简单到高级）：

1. **基本观察（无需额外工具）**：
    - 在 top 中按 f 键进入字段管理，启用查看更多列（如 COMMAND、WCHAN）。
    - 看哪些进程的 **TIME+**（累计 CPU 时间）或 **%CPU** 高，且可能是内核相关（kworker、[ksoftirqd] 等）。
    - 同时关注 wa（I/O wait）：如果 wa 高，sy 可能间接因 I/O 系统调用引起。
2. **查看系统调用频率**：
    - `用 strace -c -p <pid>（针对具体进程）或 strace -f -c <command> 统计系统调用次数和时间。`
        - 高频调用如 read/write/gettimeofday/epoll_wait 可能推高 sy。
    - 用 pidstat -d 1（sysstat 包）查看进程 I/O 和系统调用率。
3. **内核热点分析（推荐 perf）**：
    - 安装 perf（大多数发行版自带）：sudo apt install linux-tools-common 或类似。
    - 实时查看：sudo perf top -e cycles 或 sudo perf top --sort comm,dso,symbol。
        - 会显示热点内核函数（如 do_syscall_64、sys_enter_*、网络驱动函数）。
    - 采样记录：sudo perf record -a -g sleep 10 → sudo perf report 查看栈踪迹。
        - 能精确看到 sy 时间花在哪些内核路径（系统调用入口、中断处理等）。
4. **其他诊断命令**：
    - **中断统计**：cat /proc/interrupts 或 watch -n1 cat /proc/interrupts。
        - 如果某些中断（如网卡 nvme 磁盘）变化快，说明 softirq/hardirq 贡献 sy。
    - **I/O 相关**：iostat -xz 1（看磁盘利用率，如果高可能间接推 sy）。
    - **软中断**：cat /proc/softirqs 或 mpstat -I ALL 1。
    - **内核线程**：ps -ef | grep kworker 或 top 中看 kworker 高 CPU。
5. **常见导致 sy 稍高的原因（即使 3.5% 也可能有轻微）**：
    - 频繁短系统调用（gettimeofday、futex 等）。
    - 高网络流量（softirq 处理包）。
    - 虚拟化（st steal 时间高时 sy 也可能升）。
    - 定时器密集（高精度 timer）。

**总结**：sy=3.5% 表示内核态仅占 3.5%，非常健康，无需优化。除非你观察到性能问题，否则不用深挖。如果 sy 突然升高，再用 perf 等工具定位热点。你的系统很可能运行得很顺畅！如果贴 top 完整输出或具体场景，我可以帮你进一步分析。
